# Camera investigation — 2026-10-24

## Result and scope

The identified native GUI branch has been traced through the installed DLL:
camera commands reach a JSON-RPC request builder and an MQTT publish call. Pinned
Orca 2.4.0 source corroborates TLS MQTT to `<device>/request`, with replies on
`<device>/response`. This establishes the static native branch, not a camera
transaction observed on the installed printer. Alternate GUI connection backends
and direct Moonraker WebSocket camera compatibility remain unverified.

Two authentication layers are visible: native MQTT certificate configuration and
GUI image-decryption credentials returned by monitoring. The native camera
handlers rebuild parameters and omit the GUI's optional `clientid`. The GUI's
300-second timer renews or closes monitoring; it does not establish server-side
expiry. Camera tools remain unimplemented because installed-firmware behavior,
session ownership, expiry, freshness, and safe cleanup are still unresolved.

All live checks in this session were reads. No camera start/stop, print control,
upload, motion, configuration, calibration, or firmware action was issued.

## Tool results and limitations

The first full-bundle analysis used a 1 GiB worker heap and a 60-second deadline.
REA reported heap exhaustion during static analysis: zero parsed files, explicit
partial coverage, and no usable function reconstruction. A successful process
exit was not treated as successful code analysis.

An inert Babel AST pass then selected exact function ranges from the original
bundle, wrapping methods as standalone object members for analysis. The local
manifests retain byte offsets, original line numbers, and excerpt identities.
No target JavaScript was executed. REA successfully parsed seven camera excerpts
(2,252 semantic nodes / 2,266 relations) and fifteen lifecycle excerpts
(2,713 semantic nodes / 2,423 relations), using 512 MiB workers and 30-second
per-file limits. Complete coverage refers to those excerpts only; wrappers and
omitted code prevent whole-application reachability conclusions.

REA's application-feature trace for the literal camera start method returned
zero seed matches and zero paths in its application graph. That automatic trace
did not recover a transport contract from Dart's obfuscated dictionary builders.
The findings below come from inspecting the exact original ranges and their
callers, corroborated by the parsed excerpts, rather than claiming REA resolved
the entire flow automatically.

The earlier `doctor` result was **not green**: native engine and global
registration readiness were absent, and `inspect_binary_layout` returned
`capability_unavailable` because that pwntools profile supports Linux x64 only.
The follow-up uses REA's separate `execute-rizin-command` path successfully on
Windows. Ghidra remains unavailable; no native decompilation, target execution,
process attach, or whole-app reconstruction was performed. A full doctor pass
is not claimed or required for this narrower working route.

The follow-up inspected PE sections, seven selected function bodies totaling
34,540 bytes / 7,464 decoded instructions, and two adjacent virtual-table slots.
An inert, targeted RIP-relative byte search supplied candidate references;
REA/Rizin then decoded the selected instructions and read the table bytes.

the pinned source, not recovered debug symbols or runtime reachability proof.
Rizin warned that automatic string inventory skipped large sections. No absence
claim relies on that inventory; selected instruction bytes were checked against
the original DLL, and candidate strings came from direct bounded byte reads.

Seven additional exact JavaScript excerpts parsed with zero failures, a 512 MiB
worker heap and 30-second per-file deadline. Excerpt provenance records original
character offsets, lines, wrapper hashes and source identity. Complete coverage
applies only to the selected excerpts and native ranges. Raw Evidence, source

## Expiry and client ownership

Three distinct clocks must not be conflated:

- GUI monitoring policy: 300 seconds, then renew or close according to the branch
  described above. The LAN path renews without proving a camera lease duration.
- Native response callback deadline: the pinned header defaults to 80,000 ms.
  The pairing exchange instead registers 60 seconds and waits up to 70 seconds.
  These are request waits, not session expiry. [Header](https://github.com/Snapmaker/OrcaSlicer/blob/b1831e5dcb464172de33783142425aafda834fbc/src/slic3r/Utils/MoonRaker.hpp#L332-L342).
- MQTT connection policy: the source uses a 30-second keepalive and
  `set_clean_session(false)`. Neither setting defines camera lifetime or
  monitoring ownership. [MQTT constructor](https://github.com/Snapmaker/OrcaSlicer/blob/b1831e5dcb464172de33783142425aafda834fbc/src/slic3r/Utils/MQTT.cpp#L25-L57).

The GUI request builder includes optional `clientid`, but the selected native
handlers and camera builders reconstruct only `domain` / `interval` / `expect_pw`
for start and `domain` for stop. Consequently this native branch drops that field.
The MQTT connection still has a client ID; whether the printer derives ownership
from it, from the domain, from another context, or maintains shared state is
unknown. Omission does not prove that monitoring is global or that stopping is safe.

Pinned source stores the MQTT engine and response callback map in class-static
members. Its weak pointers protect callback lifetime; they do not establish
per-view or per-camera ownership. There is no demonstrated bridge-owned session
handle, reference count, safe repeated-open behavior, or close isolation. The
source's native stop sends a domain without an explicit camera owner. Any bridge
cleanup contract must wait for server/firmware evidence. No stop experiment ran.
