# Camera investigation — 2026-10-24

## Result and scope

REA is installed and was exercised through both its CLI and an actual MCP stdio
connection. Focused JavaScript analysis works. Camera access remains unresolved:
the installed GUI constructs monitor RPCs and consumes session authentication
fields, but its native bridge's printer-side wire transport, ownership guarantees,
and installed-firmware camera behavior have not been established.

All live checks in this session were reads. No camera start/stop, print control,
upload, motion, configuration, calibration, or firmware action was issued.

## Tool results and limitations

The first full-bundle analysis used a 1 GiB worker heap and a 60-second deadline.
REA reported heap exhaustion during static analysis: zero parsed files, explicit
partial coverage, and no usable function reconstruction. A successful process
exit was not treated as successful code analysis.

An inert Babel AST pass then selected exact function ranges from the original
bundle, wrapping methods as standalone object members for analysis. The local
manifests retain byte offsets, original line numbers, and excerpt identities.
No target JavaScript was executed. REA successfully parsed seven camera excerpts
(2,252 semantic nodes / 2,266 relations) and fifteen lifecycle excerpts
(2,713 semantic nodes / 2,423 relations), using 512 MiB workers and 30-second
per-file limits. Complete coverage refers to those excerpts only; wrappers and
omitted code prevent whole-application reachability conclusions.

REA's application-feature trace for the literal camera start method returned
zero seed matches and zero paths in its application graph. That automatic trace
did not recover a transport contract from Dart's obfuscated dictionary builders.
The findings below come from inspecting the exact original ranges and their
callers, corroborated by the parsed excerpts, rather than claiming REA resolved
the entire flow automatically.

`doctor` is **not green**: Node and host checks passed, but native providers and
global agent/skill registration are absent. The directory target check directed
the caller to static JavaScript analysis. A narrow `inspect_binary_layout` call
returned `capability_unavailable`: that REA pwntools profile supports Linux x64
only. Ghidra/JDK were not installed; no native decompilation was attempted.
These limitations do not prevent the completed static excerpt analysis.

## Live evidence and next probes

The real MCP read connection confirmed firmware `2.0.0.205_20260914173503` and
Moonraker `2.0.0`; `/server/webcams/list` returned an empty array. That says
nothing definitive about the proprietary camera session protocol. Earlier
404 snapshot GETs remain historical observations; they were not repeated here.

Next, trace only the native implementation reached by the GUI's `sendMessage`
camera dispatch, or obtain a bounded, sanitized capture of an ordinary supported
camera session with permission to open that session. Establish the actual socket
endpoint, auth handshake, success/error envelope, URL restrictions, expiry,
client ownership, repeated-open behavior, and whether closing one client affects
others. Confirm image size limits, timestamps and freshness separately. Do not
guess start parameters on the live printer, bypass authentication, or stop an
existing client's session. Camera tools remain unimplemented until this is known.
