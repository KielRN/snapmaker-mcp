G-code dialect. The software path is verified against local HTTP simulation and
the actual MCP stdio process. No live printer upload, camera operation, print

## Implemented contract

Preparation accepts a canonical UUID4 operation ID, absolute allowlisted path,
plate number and explicit one-based physical mapping for each logical filament
entry. The receipt ID is the preparation operation ID. It binds file bytes/hash,
all inspected requirements, mapping, normalized material/feed evidence, private
printer/job identity digest, local validation policy and a default 600-second
expiry. The plate number labels this single exported file; it does not select a
plate from a container. Neither preparation nor upload authorizes a print.

File reads resolve allowed roots and inspect the opened file handle to close the
resolve/open symlink race. Windows junctions are included; Linux requires
`/proc/self/fd`. Unsupported handle-verification platforms fail closed. Only
regular `.gcode` files are accepted. Defaults cap bytes at 32 MiB (configurable
up to 128 MiB), lines at 500,000 and each raw line at 8,192 bytes. Parsing uses
two bounded passes without an expanded command list, in a worker thread.

The dialect accepts G0/G1, G4, G21, full G28, G90/G91, E-only G92, M82/M83,
M104/M109, M140/M190, M106/M107, M400 and T0–T3 within declared array length.
It rejects unknown commands/parameters, arcs, transforms, partial homing,
firmware controls and macros. Coordinates must become explicit after homing;
absolute E requires a G92 reset after each tool selection. The inspection
envelope is 0–270 mm per axis, 300 °C nozzle, 100 °C bed and 60,000 mm/min feed;
these are conservative software policy, not measured printer limits. It checks
commanded targets and requires a >=170 °C M109 wait before nonzero E moves;
this is not a measured temperature guarantee or polymer suitability test.

Required comments are `filament used [mm]`, `filament used [g]`, `filament_type`,
`nozzle_diameter`, `filament_diameter`, and `layer_height`. Arrays contain one to
four matching entries; material is PLA/PETG/ABS/ASA/TPU, diameter is 1.75 mm,
nozzle is 0.2/0.4/0.6/0.8 mm, layer height is positive and at most 80% of the
smallest nozzle. Every consumption entry participates, including later positive
entries after a zero first entry. Nonzero E also marks a used tool. Used tools
require positive mm/g declarations; accumulated net-extrusion high water cannot
exceed declared mm by more than 0.1 mm. This does not measure spool availability
or independently establish material mass, flow calibration or final quality.

The current mapping must match the explicit mapping. Used physical tools require
positive completed feed and enabled toolhead sensors, successful RFID read,
matching RFID/configured material, and matching locally attested nozzle size.
Nozzle sizes are local operator configuration; they are not sensed by this
bridge. All normalized mapping/material/feed evidence is bound conservatively,
so changes on an unused tool can also invalidate a receipt. Job settings are
inspected and retained; no printer job parameters are applied in this milestone.

Upload requires fresh idle, identity, job, mapping and material evidence before
POST; it rechecks after destination preflight. An OS file lock plus an async
lock serializes coordinators sharing **one receipt database per printer**. The
claim and inflight intent commit atomically before dispatch, with SQLite FULL
synchronization. Names derive from UUID/hash, not local filenames. Preexisting
destinations block upload. Another independent client can still race these reads;
this protocol provides no atomic create-if-absent or global printer lock.

Multipart uses `root=gcodes`, empty `path`, `print=false`, SHA256 checksum and
the selected bytes. An acknowledgment must name exactly the generated relative
destination with root `gcodes`, and explicitly report both started/queued false.
The bridge ignores Location headers, follows no redirects, and downloads only
its generated destination from the configured origin. Raw-byte deadlines,
compression refusal, bounds, HTTP errors and HTTP-200 error objects apply.
Success requires matching remote size and SHA256 plus fresh bound evidence.

## Recovery and interpretation

- A repeated ID with different arguments returns `operation_conflict`. Repeated
  successful/terminal uploads return historical results, with their original
  observation and expiry. They are not fresh file/material observations.
- Each preparation can claim at most one upload. An expired preparation cannot
  initiate a POST. Reconciliation may read an expired receipt to establish past
  byte transfer; the original expiry stays visible and conveys no start authority.
- A timeout, disconnect, cancellation or restart leaves durable inflight/unknown
  state. Repeating the ID only reads and hashes the recorded destination. Absence
  remains unknown because a late write is possible; it never triggers a retry POST.
- A matching download can reconcile a lost reply. `response_flags_confirmed=false`
  then honestly records that the acknowledgment was not seen; only bytes and bound
  idle evidence were observed. The no-start/no-queue behavior relies on the pinned
  `print=false` contract and still requires hardware acceptance.
- Bad acknowledgment paths/flags and hash mismatches are terminal for that ID;
  they cannot later be upgraded by a repeated request. There is no remote cleanup
  or delete tool. Investigate the supported app before deciding on a new operation.
- Errors before dispatch distinguish local/printer rejection from unavailability.
  After dispatch, unverifiable effects remain unknown. Results expose fixed codes
  and safe guidance, never raw printer errors, local paths or identity strings.
  A printer error envelope records rejection, not proof that no partial file
  was stored; no remote artifact cleanup is implied.
- Keep the ignored journal and its lock together. Do not delete/reinitialize them
  to retry an uncertain operation. There is no automatic receipt pruning.

material/mapping changes, expiry, duplicate IDs/claims, HTTP-200 errors, corruption,

software checks. Final test/build results are recorded in PROJECT_STATE.md.
